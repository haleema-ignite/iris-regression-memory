# Review and fixes, 2026-09-02

The trial registry was reviewed against the real `iris-web`, `iris-api` and
`iris-sp-engines` checkouts, rather than against the fixtures. This records what
was wrong and what changed, so the trial's claims can be read accurately.

## The three findings that mattered

**1. The flagship truth did not detect its own regression.**
`IRIS-TRUTH-0001` was a substring check for `Generate Campaign` and
`onGenerateCampaign` in `PublisherCalendarHeader.tsx`. In the real file both
strings also appear in comments (lines 297 and 320) and in the prop declaration
(lines 27 and 48). Deleting the entire button block while leaving the comments
behind — the realistic shape of the original incident — still reported PASS:
"Required product text is still present". The overall verdict was FAIL, but only
because of the unrelated `0003` ratchet, so the change would have been flagged
for the wrong reason while the actual regression was explicitly cleared.

Fixed by matching against a comment-stripped view of the file and requiring the
label to appear as JSX text (`>\s*Generate Campaign`) rather than anywhere in the
source. Verified: the same deletion now reports FAIL, attributed to this change.

**2. Two truths failed on every pull request that selected them.**
`IRIS-TRUTH-0012` required the literal strings `fail closed` and `includeHidden`,
which matched nothing but a fixture written to contain
`return "fail closed"` — code shaped to satisfy the matcher rather than code
anyone would write. `IRIS-TRUTH-0015` was scoped to
`engines/brand-messenger`, which never writes `doc_src_id` — that is a Care
`doc_document` column written by iris-api.

`0015` is now a `gap`: the fact is real, the guard is not there, and recording
that honestly beats a live truth that fails every branch.

**`0012` was also demoted, and that was a mistake** — see the third pass below.
The demotion rested on reading a dirty local feature branch that predated the
IRISNG-3231 fix. The fix is on both canonical branches, and 0012 is now `live`
again, keyed to the tokens the real implementation uses.

`IRIS-TRUTH-0005` was described here as a third standing failure, on
`provider: 'applebc'`. That was the same provenance error: the string appears on
neither canonical branch. Switching it to `added_lines` was still the right
change — it keeps all three historical detections and cannot ratchet — but the
premise stated in this section was wrong.

**3. The emitted Semgrep rule contradicted the truth it compiled.**
`IRIS-TRUTH-0019` states it is "a reintroduction check on added lines, not a
leftover ratchet". The internal executor honoured that; the emitted rule was a
whole-file `pattern-regex` at `severity: ERROR`. Dropped into the iris-api
Semgrep config as the manifest instructed, it would have produced **78 findings
across 11 files** on the first run. Emitters are now split: `semgrep.yml` for
whole-checkout truths, `semgrep-diff-scan.yml` for added-lines truths, the latter
carrying `requires_diff_scan` metadata and a header stating it must run with
`--baseline-commit`.

## What the benchmark actually measured

34/34 is reproducible, but several qualifications belong next to it — and the
metric itself was measuring less than it claimed. See the fourth pass below.

The evaluator recorded each case's `contract` and never checked it. The manifest
is now `schemaVersion: 2` with per-truth expectations — `mustFailTruths`,
`mustPassTruths`, `mustNotFailTruths` — and the evaluator scores against them.
`summary.casesMeetingNamedExpectations` is the number to quote, currently 34/34.

The single `contract` field could not express a fix case at all: PRs 860 and 921
are the *fix* for IRIS-BEH-0007, so `IRIS-TRUTH-0005` must pass there while the
overall verdict fails on the unrelated `0009` leftover. Under one field they read
as failures of attribution when they were nothing of the kind.

`control-care-history-1102` was labelled "newly adds a leading-wildcard LIKE".
It does not. Its only `LIKE` change adds a table alias to a wildcard that already
existed:

```diff
-            AND his_metadata LIKE '%"reason":"STOP_KEYWORD"%'`,
+            AND h_opt.his_metadata LIKE '%"reason":"STOP_KEYWORD"%'`,
```

The original `fail` came from treating a modified line as an added line — the
false positive that fired on every reformat of those 78 pre-existing wildcards.
The case is now `expected: pass`. `0019`'s positive detection is still validated
on real history by `culprit-legacy-care-574`, and by a unit test.

Every benchmark case was `iris-api` or `iris-sp-engines`, so `0001`–`0004` — the
Generate Campaign family — had no real-history coverage at all. That is exactly
where the false negative was. The real removal (`040a6668`) and its revert
(`ae0c4061`) are now cases: 0001 and 0002 fail as `introduced` on the removal and
pass on the revert.

## Signals that could never fire

Seven live truths carried signals that were English descriptions of a failure
rather than tokens that appear in TypeScript: `fail open`, `skip persistState`,
`in-memory only dedup`, `engine-wide auth failure`, `verify against CONFIG only`,
`ignore page appSecret`, `skip getMessagingUserProfile`, `Date.now() as dedup`,
`uuid as message id`, and others. None of them carried a single detection in the
benchmark; every real detection came from a real code token, a real log string,
or a regex over real syntax. They are removed, and a test now fails if one comes
back.

Two were removed for the opposite reason. `Math.random()` was forbidden across
every Facebook and Instagram webhook and polling path, which is the ordinary way
to jitter a retry backoff. `JSON.stringify(parsedBody)` is a real anti-pattern
and was kept, but it appears today only inside a comment in the Instagram webhook
explaining why not to do it — comment-stripped matching now ignores that.

## Engine correctness fixes

- **Comment stripping** everywhere, string- and template-literal safe, with line
  counts preserved. Two bugs surfaced while building it, both found by running
  the stripper against adversarial input rather than by reading it:
  - a regex literal ending in `//` (`/https:\/\//`) read as a line comment and
    discarded the rest of the line, silently losing any token a truth needed to
    match there;
  - adding regex-literal handling then made `<` a position where a regex could
    start, so every JSX closing tag `</div>` swallowed the rest of its line and
    any comment after a closing tag survived — reopening the comment-ghost
    bypass in precisely the `.tsx` files the fix was for. `<` and `>` are no
    longer regex-start positions, with `=>` readmitted explicitly (see the
    second pass below, which is how that regression was caught).
- **Reformatted lines are not new violations.** A modified line arrives as both
  removed and added. Reporting only when the count of violating lines increases
  removes the noise on refactors without missing a genuinely added violation.
- **Added and removed lines are paired one-for-one.** The first version of that
  suppression used set membership, so copying an already-violating query into a
  second call site — two identical added lines against one removed — answered
  "this line was also removed" for both copies and reported nothing. That missed
  the most ordinary way a bad query spreads. Pairing by count keeps the reindent
  and PR-1102 cases passing while catching the copy.
- **A failing advisory truth is no longer described as holding.** A
  `blocking: false` truth that failed produced the headline "SELECTED TRUTHS
  HOLD" above its own rendered failure, and a green check. It now reports
  `advisory_fact_failed`, and still never gates.
- **Removed-guard detection is per file** and consults the file's full
  after-state. Previously a token surviving in a different changed file masked a
  real removal, and a guard living outside the diff hunk read as deleted.
- **Required guards must hold together in one file.** They were joined into a
  single haystack, so guard A in one file and guard B in another satisfied a rule
  whose point is that both appear at the same decision site.
- **The contract query window** is the enclosing blank-line-bounded block, not
  ±25 lines. The old window reached into unrelated neighbouring queries; a
  single-statement scope broke legitimately dynamic filter composition, so
  neither extreme is used.
- **Coverage means inspection.** A file was counted covered if any `always_on`
  truth was selected, so a one-line comment change to an unrelated reporting util
  reported "coverage: full" for a file nothing opened — and that fed the check
  conclusion.
- **Delegated is not a pass.** A CodeRabbit hand-off returned `pass` and counted
  toward "verified holding". It now returns `delegated`; if every selected truth
  is delegated the assessment is `inconclusive`.
- **Diff parsing** tracks hunk boundaries, so a removed line whose content starts
  with `--` is no longer dropped as a file header.
- **Misconfiguration is rejected at load**, not reported as a failed fact against
  whichever pull request selected the truth. An undeclared repository, a product
  truth that asserts nothing, `require_present` without signals, and
  `emit: semgrep` with nothing to compile all fail the load.
- **Workspace scans** skip generated, minified and binary files, and are bounded.
- **`--workspace` and a declared `--repo` are required.** A missing checkout
  reconstructed files from hunk context, and a mistyped repository selected zero
  truths and reported a clean-looking abstention.

## Second pass: bugs found by adversarially testing the fixes

The fixes above were then reviewed independently, by running them rather than
reading them. That found seven more defects, including two introduced by the
fixes themselves. Worth recording, because the pattern is instructive: every one
of them was invisible to inspection and obvious to a two-line test.

- **A whole-checkout ratchet narrowed to the changed files.** `workspaceBodies`
  short-circuited its workspace listing whenever the change touched an in-scope
  file, so `mode: workspace` inspected only that pull request's files. The
  ratchet was therefore *loudest on changes that touched nothing relevant* and
  silent on changes to the directory it guards — precisely backwards. The
  listing is now unioned with the change's files, not replaced by them.
- **Excluding `>` to fix `</div>` broke `=>`.** `.filter(u => /\/\//.test(u))`
  truncated at the regex's own `//`. Distinguishing an arrow from a JSX closing
  tag needs the character before the `>`.
- **The `#` stripper ate real code.** `$#`, `${path#prefix}` and
  `url=https://x/y#frag` all lost the rest of their line. A marker now only
  opens a comment at a whitespace boundary.
- **An apostrophe hid a `#` comment.** `- name: don't run this  # disabled` —
  the lone apostrophe was read as opening a string literal, which swallowed the
  `#`, so a commented-out token stayed readable as code. That would have let a
  promotion workflow whose e2e selection was commented out satisfy
  IRIS-TRUTH-0003. Quotes now only protect a marker when balanced on that line.
- **The `*` comment-continuation rule blanked generator methods.** `*gen() {}`
  and `*[Symbol.iterator]() {}` are code. The `*` must now be followed by
  whitespace, `*`, or `/`.
- **One executor throwing aborted the whole run.** `assess` had no guard around
  `runExecutor`, so a single unevaluable truth discarded every other finding. It
  is now caught per truth and surfaced as a non-blocking, clearly-labelled
  finding.
- **`validateExecutorShape` did not cover `pattern`, `contract` or `semgrep`.** A
  live truth of those kinds with zero assertions loaded cleanly, passed on every
  change, and counted toward coverage — the invented pass the validation exists
  to prevent.
- **The ReDoS guard rejected one shape and missed three worse ones.**
  `(a|a)*`, `(a{1,}){2,}` and `(a*|b)+` all passed; the last takes nine seconds
  on a 28-character input. The guard now rejects any quantified group whose body
  contains a quantifier or an alternation, and a test asserts every pattern in
  the shipped registry still compiles.
- **The manual assess workflow could never succeed**, because it passed
  `--repo $GITHUB_REPOSITORY` — this compiler repository, which no IRIS truth
  applies to. Removed rather than left as a broken entry point.

Smaller, also fixed: an empty scoped file counted as a missing guard; the diff
parser inferred `status: deleted` from an *added line* containing the text
`deleted file mode`; the unknown-repository error printed lowercased names; and
per-line cache entries evicted whole-file ones.

## Third pass: a provenance error, and four more correctness bugs

A second reviewer checked this work against the repositories and found something
worse than a bug: **three truths had been written from dirty local feature
branches**, and the conclusions drawn from them were wrong.

- `IRIS-TRUTH-0012` was demoted to `gap` on the belief that the community engine
  had no hidden-board handling at all. The IRISNG-3231 fix is present on **both**
  canonical branches — `resolveBoardVisibility`, `cfg.includeHidden` and the
  `'unknown-board'` drop are all there. The local branch
  (`codex/youtube-multi-channel-runtime`, dirty, 84 modified files) simply
  predated it. 0012 is restored to `live`, now keyed to those three real tokens.
- `IRIS-TRUTH-0020` claimed "7 of 28 engines". The real counts are 6 of 28 on
  `origin/main` and 8 of 29 on `origin/develop`. Seven matched neither.
- A proposed `IRIS-TRUTH-0022` asserted a Meta webhook fix had been reverted. It
  had not — the guard is on `origin/develop` and had not yet reached `main`. The
  truth was deleted.
- `IRIS-TRUTH-0005`'s "standing failure" was also a branch artefact:
  `provider: 'applebc'` appears on neither canonical branch.

`docs/truth-authoring.md` now requires repository, branch, SHA and clean/dirty
for any current-state claim, and `docs/iris.md` carries a by-branch table.

The same pass found four more correctness bugs:

- **Attribution was "did you touch the file".** A change editing
  `content-sources.service.ts` without adding any SocialGateway gate was reported
  as having *introduced* `IRIS-TRUTH-0009`. Attribution is now settled by
  evaluating the truth against the base state: holds at base and fails at head is
  `introduced`; fails at both is `preexisting`; no base state is `unknown` and
  never gating. `--base-ref` materializes the base with `git archive`.
- **The diff and the checkout could describe different revisions.** A diff
  deleting Generate Campaign, assessed against a healthy checkout, passed. For
  `--pr` the CLI now verifies the checkout is at the head and clean; for
  `--diff-file` the report is labelled `Revision: UNVERIFIED`.
- **A multiline block comment still produced findings.** Stripping each diff line
  in isolation cannot see that a line sits inside `/* ... */`. Added lines are now
  located by hunk line number in the comment-stripped whole file, with a
  self-check that falls back to per-line stripping if the mapping disagrees.
- **`IRIS-TRUTH-0008` still failed pure query reformats**, because it used raw
  added lines to dodge an alignment problem the line-number mapping has now
  removed. It uses paired lines again.

Two more, from making those fixes:

- **An added-lines pass was still reported as "verified holding".** Results now
  carry a proof scope: `workspace_fact_holds`, `no_reintroduction_detected`,
  `delegated` or `not_evaluated`, rendered under separate headings. Every live
  added-lines truth must declare `proves`, enforced at registry load.
- **My own narrowing of `IRIS-TRUTH-0019` introduced catastrophic backtracking.**
  An unbounded `[^\n]*` gap retried from every column match: two benchmark cases
  went from ~2s to **4970s and 2259s**. Gaps are now bounded, regex matching
  skips lines over 4000 characters, and a test rejects any shipped pattern with an
  unbounded gap.

Also: executor errors are now an `error` verdict rather than a failed fact,
proposals moved to a "registry health" section so they are not per-change noise,
and coverage is described as "in scope of a live truth" rather than "inspected".

## Fourth pass: a repeat of the fixture-shaped mistake

A further review found three blockers, and the first is the same error I had
just spent a whole pass criticising.

**`IRIS-TRUTH-0012` falsely failed canonical code.** The generic checker
required every `required_signals` token in one file, but the guards live in two:
`resolveBoardVisibility` in `polling.component.ts`, `cfg.includeHidden` and
`'unknown-board'` in `filtering.ts`. So the restored 0012 failed both
`origin/main` and `origin/develop`. The unit test missed it because the fixture
put all three tokens in **one synthetic file** — a fixture written to satisfy
the matcher, which is exactly the failure mode this registry exists to prevent.

Fixed with `required_signal_groups`: each group must hold together within one
file, and different groups may live in different files. The fixture now mirrors
the real two-file split, and `npm run probe:canonical` materializes named refs
and checks the registry's current-state claims against them — because a unit
test cannot catch an error in the premise.

**`trial:local` labelled a dirty filesystem as `HEAD`.** The four checkouts
carry 47/42/66/2 modified and 19/51/33/6 untracked files, so those results
described nobody's commit. It also preferred local `main` over `origin/main`
(all four differ, making results machine-dependent) and silently skipped
untracked files while claiming to assess uncommitted work. Now: the HEAD audit
materializes the real commit; the filesystem run is labelled `WORKTREE` with
modified and untracked counts; the base ref and SHA are printed; remote-tracking
refs are preferred; diffs are taken from the merge base; and untracked files are
included as additions.

**PR mode did not use the PR's true comparison base.** It originally returned
`unknown` unless the caller passed `--base-ref`; the first repair then used
GitHub's `meta.baseSha`, which is the target branch's current tip and can advance
after the feature branch diverges. PR mode now computes and materializes the
merge base of `meta.baseSha` and `meta.headSha`, exactly as local mode does. If
that common ancestor is unavailable it reports unattributed findings rather
than substituting the target tip and blaming someone else's later commits on
the PR.

### The benchmark metric was measuring less than it claimed

"Zero false positives" was true only per case: on an expected-fail case an extra
wrong truth failure changed nothing, and 23 cases constrained nothing at all.
Expectations are now exhaustive — every failing truth must be named in
`mustFailTruths` or `alsoAllowedToFail` — and `perTruthAccuracy` is renamed
`casesMeetingNamedExpectations`, which is what it actually measures.

Turning it exhaustive immediately surfaced five real detections the old scoring
had hidden, and all five are correct: `0019` genuinely fires on PR 574, and
`0006` genuinely fires on four iris-api trees carrying
`intMetaOverride.apiParams = {`. Both are now required. The `0006` occurrence is
absent from both canonical branches, so it is historical rather than live.

The suite is now documented as a tuned regression suite rather than validation.
The truths were derived from these incident families and two case labels were
corrected after review; a suite you tuned against cannot measure your own
accuracy. Prospective read-only pull-request results are the real validation
and are recorded separately from the tuned historical score in
`docs/prospective-trial-2026-09-03.md`.

Also: the README outcome table still described the removed attribution bug; the
runner omitted gap `0015`; it claimed an MCP surface it never exercised (now
stated honestly, with a registration test); and the emitted Semgrep YAML was
only checked structurally (`npm run verify:semgrep` now runs the real CLI when
installed and says so plainly when it is not;
`npm run verify:semgrep:required` fails closed for release qualification).

## Attribution, and why it changes the rollout

Failures are now classified `introduced` (evidence from added lines, or in a file
this change touched) or `preexisting` (a standing ratchet against the checkout).
Only `introduced` can fail a check, in either enforcement mode; pre-existing
findings are reported as neutral, and SARIF emits them at `note` rather than
`error`.

Before this, a one-line comment change to `src/features/reporting/utils/` in
iris-web reported `FACT FAILED` with "coverage: full". Every iris-web pull
request and every in-scope iris-api pull request would have failed permanently on
`0003` and `0009`. That is the fastest way to teach a team to ignore a check.

## Three new proposals, not new checks

Recorded as `proposed` because each needs an owner's decision, and guessing would
encode the wrong thing:

- **`0020`** — only 7 of 28 engines call `configureDualPublish`. Requiring all of
  them would report 21 failures on day one.
- **`0021`** — `IRIS/CLAUDE.md` documents Kafka `sessionTimeout` 120000 /
  `rebalanceTimeout` 120000 / `heartbeatInterval` 5000.
  `sdk/src/kafka-consumer.ts:52-54` sets 10000 / 30000 / 3000. One is stale.
- **`0022`** — `engines/facebook/src/webhook/webhook.component.ts:280` verifies
  HMAC against the single process-wide `CONFIG.FACEBOOK_APP_SECRET`, and neither
  `getWebhookSecretCandidates` nor `verifyMetaWebhookSignature` exists in the
  tree. That is the state `IRIS-TRUTH-0011` exists to prevent, and `0011` cannot
  see it because it only inspects added lines.

`0022` is the one worth reading first: it suggests a fix may have been reverted or
renamed.

## Trial posture

Unchanged in intent, enforced in code. There is no assess workflow at all now —
the one that ran on every `pull_request` with `enforcement: error` is gone, and
its `workflow_dispatch` replacement was removed once it turned out it could
never have worked. `tenant.yaml` and `action.yml` default to `warning`, the
example service workflow is marked do-not-copy, and only a truth this change
*introduced* can exit non-zero even under `error`. `docs/rollout.md` holds the
promotion criteria.
